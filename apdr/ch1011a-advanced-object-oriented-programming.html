10.1 Objects, references, and copying

Assignment creates another route to an object; it does not duplicate a mutable value. A copy makes a new outer container, and a deep copy recursively copies referenced parts where the copy protocol allows.

In plain words: an object is the value with identity and behaviour; a reference is a way to reach it; an alias is another name or container entry that reaches the same object.

Binding and copyingb = a binds b to the object already named by aFor compound objects, copy.copy makes a shallow copy; copy.deepcopy recursively copies supported parts and may copy too much. Python copy documentation.

In CPython, names refer to objects; assignment changes a binding. Mutating a list through either alias is visible through the other. CPython may reuse some immutable objects, so identity observations such as 256 is 256 are not a value-comparison rule. A shallow copy creates a distinct outer list but keeps references to nested items. A deep copy uses a memo to handle cycles and can be customised by a class.

Worked example · nested aliases

  1. a = [[1], [2]] creates an outer list and two inner lists.
  2. b = a.copy() creates a new outer list; a is b is false.
  3. a[0] is b[0] is true, so b[0].append(9) changes the nested list seen through a.
  4. For independent nested lists, use a suitable deep-copy operation; check whether custom objects or resources should remain shared.

Trace aliases and copies

Trap: is tests identity, not value equality; use == when equal contents are the question.

Near miss: Copying only the outer list does not isolate a nested mutable item; copy that item too if independent mutation is required.

Recall · §10.1

  1. What does assignment do to a name?
  2. What remains shared after a shallow copy?
Answers
  1. It binds the name to an object; assignment itself does not copy that object. §10.1
  2. References to nested items remain shared. §10.1

10.2 Memory, attributes, and object layout

Python gives objects a flexible interface, while CPython implements them with runtime structures. Instance dictionaries are convenient; slots can reserve known attributes. Attribute access also follows descriptor precedence, so a simple dictionary search is only a sketch.

In plain words: an instance dictionary is the usual place for per-object attributes; slots declare a fixed set; a descriptor is a class attribute that controls access.

Instance attribute lookup (simplified precedence)data descriptor → instance → class value → fallbackThe exact lookup is defined by object.__getattribute__ and may be customised. Descriptor guide.

In CPython’s C API, a regular object header includes a reference count and a type pointer; variable-sized objects add size information. These are implementation details: do not write application logic around a claimed byte size or directly access the fields. Many objects are tracked differently by the garbage collector; reference counting alone cannot reclaim unreachable cycles, so a cyclic collector complements it. C object structures · garbage collector.

Worked example · a slotted point

  1. A point always needs x and y, so declare __slots__ = ("x", "y").
  2. Instances can assign those names; an undeclared attribute raises AttributeError when no base class supplies a dictionary.
  3. Add "__dict__" to the slots only if arbitrary instance attributes are part of the design.
  4. Check the trade-off: fixed attributes and possible memory savings versus less flexibility; do not assume a universal byte count.

Trace slots and attribute lookup

Trap: A non-data descriptor can be shadowed by an instance attribute; a data descriptor takes precedence over it.

Near miss: __slots__ on a subclass does not remove a dictionary inherited from a base class that provides one.

Recall · §10.2

  1. Which kind of descriptor wins before an instance dictionary?
  2. What changes when a class declares slots without __dict__?
Answers
  1. A data descriptor. §10.2
  2. Instances are limited to declared slots unless a base class or explicit slot provides a dictionary. §10.2

10.3 Types, protocols, and substitution

Nominal checks use declared class relationships; structural compatibility asks whether the needed operations are present. A type contract is useful only if implementations honour the behaviour that callers rely on. Gradual type hints let checked and unchecked code coexist; user-defined generic classes are invariant by default unless their type parameter is covariant or contravariant. Static analysers approximate program behaviour to find likely mistakes without executing every path.

In plain words: nominal typing recognises named inheritance; structural typing recognises the required shape; substitutability means a replacement preserves the caller’s expectations.

Function-type varianceaccepted inputs may widen · promised outputs may narrowA subtype should accept at least the inputs its parent accepts and return values meeting the parent’s promise.

typing.Protocol describes a structural interface for static type checkers. A protocol annotation does not add a runtime check. A protocol marked @runtime_checkable allows a limited runtime membership check that checks attribute presence, not full signatures. Abstract base classes provide a nominal mechanism and can prevent instantiation while abstract methods remain.

Worked example · a readable protocol

  1. A reporting function needs only write(text).
  2. Describe that operation in a Protocol; a logger with a compatible method can satisfy a static checker without inheriting from the protocol.
  3. If the logger accepts fewer kinds of text than callers may provide, the contract is not substitutable.
  4. Use an ABC when explicit shared implementation or nominal registration is actually needed.

Compare protocols and substitution

Trap: An annotation does not validate runtime values by itself.

Near miss: A subclass method that rejects a valid base-class input narrows the accepted contract and can break callers.

Recall · §10.3

  1. What does a Protocol primarily support?
  2. How do safe method arguments and results vary in a subtype?
Answers
  1. Structural compatibility checking by static type checkers. §10.3
  2. Arguments may be accepted more broadly; results must meet at least the original promise. §10.3

10.4 MRO and cooperative inheritance

Multiple inheritance needs a predictable order for finding methods. Python’s C3 linearisation preserves each class’s declared base order and the order already established by its parents; inconsistent hierarchies are rejected.

In plain words: the method resolution order (MRO) is the sequence of classes searched for an attribute; cooperative inheritance lets each class continue that search with super().

C3 merge ruleL[C] = [C] + merge(parent MROs, bases)Choose a list head that appears in no other list’s tail; remove it from all lists and repeat. No valid head means the hierarchy conflicts.

For D(B, C) where both B and C inherit from A, the merge gives D, B, C, A, object. The search respects B before C, while moving A behind both parents. super() means the next implementation in this MRO, not simply “the parent”.

Worked example · diamond lookup

  1. Set class B(A), class C(A), then class D(B, C).
  2. Start with L[B] = [B, A, object], L[C] = [C, A, object], and the base order [B, C].
  3. B is a valid head, then C is valid; A must wait until both parent branches are respected.
  4. The final order is D, B, C, A, object; inspect it with D.__mro__.

Build a C3 diamond

Trap: A depth-first walk can violate local base order; use the actual MRO.

Near miss: Repeating a shared base in a mixin method without calling super() can stop the cooperative chain early.

Recall · §10.4

  1. What does C3 preserve?
  2. Where does zero-argument super() continue?
Answers
  1. Local base order and the monotonic parent ordering. §10.4
  2. At the next class in the instance’s MRO after the current class. §10.4

10.5 Descriptors and class creation

Descriptors make properties and bound methods work through a shared attribute-access protocol. Class hooks and metaclasses extend the class-creation step; choose the smallest hook that expresses the requirement.

In plain words: a descriptor is an object on a class that participates in reading, writing, or deleting an attribute; a metaclass is the type that creates a class object.

Descriptor operationsread → __get__ · write → __set__ · delete → __delete__A normal function is a non-data descriptor; instance access binds it as a method. The metaclass creates a class object, and its __new__ method can inspect or alter the class namespace during creation. A descriptor defining __set__ or __delete__ is a data descriptor.

property, staticmethod, and classmethod use descriptor behaviour. A function fetched from a class is unbound; through an instance its descriptor returns a method that supplies the instance. For subclass registration, __init_subclass__ or a class decorator is often simpler than a custom metaclass.

Worked example · method binding

  1. class A: def f(self, x): … stores a function as A.__dict__["f"].
  2. A.f accesses it with no instance, so the function is returned without a receiver bound.
  3. A().f invokes the function descriptor with that instance and returns a bound method.
  4. Calling A().f(3) supplies the instance and 3; the method body receives both arguments.

Trace descriptor binding

Trap: A descriptor’s __get__ protocol is invoked by attribute access; the class dictionary still contains the descriptor object.

Near miss: Use a metaclass to register every subclass only if __init_subclass__ cannot satisfy the registration rule.

Recall · §10.5

  1. What does function descriptor access through an instance create?
  2. Which simpler hook can observe subclass creation?
Answers
  1. A bound method that supplies the instance as the first argument. §10.5
  2. __init_subclass__ on a base class. §10.5

11.1 Dispatch and language architectures

Languages choose different points at which to select an implementation. Static, virtual, single, and multiple dispatch describe selection rules; they do not by themselves determine the total speed of a program.

In plain words: dispatch selects which implementation handles a call; single dispatch usually selects by one receiver or argument; multiple dispatch selects using several argument types.

Python single dispatchfunctools.singledispatch → first argument typesingledispatchmethod dispatches on the first non-self or non-cls argument. See the functools documentation.

Static languages may bind a non-virtual call at compile time; virtual dispatch selects by runtime class. Python performs dynamic lookup and supports runtime replacement, while modern interpreters may optimise common call sites. Avoid assigning one fixed cost to all dynamic calls. When an operation depends on a pair of types, conditional logic, a visitor, or a multiple-dispatch library may be appropriate; the standard library’s singledispatch is not pairwise dispatch.

Worked example · collision dispatch

  1. The function collide(a, b) has two relevant types.
  2. singledispatch can select on a but does not select directly on the pair (type(a), type(b)).
  3. If behaviour differs for each pair, write explicit branching, use a visitor, or choose a library with a clear multiple-dispatch contract.
  4. Keep the choice visible to callers and test the supported combinations.

Choose a dispatch rule

Explore the dispatch and design choices

Trap: Dynamic dispatch does not imply a particular measured slowdown; benchmark the actual call path.

Near miss: Registering a handler for the first argument’s class does not distinguish two values of the second argument.

Recall · §11.1

  1. Which argument does singledispatch use?
  2. What should guide a performance claim?
Answers
  1. The first argument. §11.1
  2. Measurements on the relevant implementation and workload. §11.1

11.2 Patterns and object construction

Patterns name recurring ways to separate a client from a changing algorithm, collaborator, or product family. Use a direct constructor until configuration, substitution, or coordination makes a pattern useful.

In plain words: a strategy is an interchangeable algorithm; an observer is a registered recipient of changes; a factory chooses how to make an object; a builder assembles a complex value in steps.

Factory boundaryclient → factory → compatible productAn abstract factory creates a related family; a factory method lets a subclass choose a product; a simple factory may be only a function.

The Borg pattern shares state between instances; a singleton restricts instance creation. A module is normally imported once per interpreter process, but this does not make it a universal cross-process singleton. Dependency injection supplies collaborators from outside, which makes replacements easier to test.

Worked example · swap a logger

  1. A service depends on the behaviour log(message), not on a concrete logger class.
  2. A factory chooses a text or JSON logger from configuration.
  3. The service receives that logger through its constructor; tests can pass a recording fake.
  4. If one setting chooses a single product, a small function may be enough; use an abstract factory only when several related products must stay compatible.

Select compatible collaborators

Trap: A builder object is mutable configuration; the built request should not accidentally keep a mutable headers dictionary that later builder calls change.

Near miss: Use a singleton when identity is a real requirement, not merely to make access convenient.

Recall · §11.2

  1. When is an abstract factory more useful than a simple factory?
  2. What makes a dependency easy to replace in tests?
Answers
  1. When the client needs a compatible family of related products. §11.2
  2. Depend on a behavioural contract and inject the collaborator. §11.2

11.3 Quirks and decorator DSLs

Several surprising behaviours come from when Python evaluates a definition and what a closure captures. Decorators turn definition-time functions or classes into registries and other small domain-specific languages.

In plain words: a mutable default is created when the function is defined; late binding reads a closure variable when the function runs; name mangling changes a class’s double-underscore attribute name to reduce accidental clashes.

Capture-at-definition fixesdef f(x, values=None): … · lambda i=i: iUse a sentinel to create a fresh mutable value per call; use a default argument or a separate factory to capture a loop value.

Double underscores do not create security privacy. Monkey patching changes a name or attribute at runtime, so keep its scope small and patch where the code under test looks it up. A decorator factory can capture configuration, register a function or class, then return the original object or a wrapper.

Worked example · route registry

  1. Create a dictionary named routes.
  2. route(path) returns a decorator that records the function under that path.
  3. Apply @route("/home"); the function is registered when its definition executes.
  4. Look up and call the registered function later; duplicate-path behaviour should be defined by the application.

Trace defaults and registration

Trap: A default list is shared between calls; None is a common sentinel for creating a fresh list.

Near miss: lambda: i in a loop closes over the changing name; lambda i=i: i captures the current value as a default.

Recall · §11.3

  1. When is a function’s default value evaluated?
  2. What does name mangling protect against?
Answers
  1. When the function definition executes. §11.3
  2. Accidental name collisions in subclasses; it is not a security boundary. §11.3

Exam-style problems

1 · Storage, lookup, and inheritance · 20 minutes

A library defines a slotted Record base, a mixin that adds a computed label property, and two subclasses arranged as a diamond. A caller shallow-copies a record’s list of tags.

  1. Trace whether the copy and original share the outer list and nested tag values. (3 marks)
  2. Explain how the property participates in attribute lookup and whether a same-named instance value wins. (3 marks)
  3. Write the C3 order for Final(Left, Right) where both inherit from Base. (2 marks)
  4. Give two checks before relying on __slots__ to restrict storage. (4 marks)
Show worked answer
  1. A shallow copy creates a new outer list, but nested mutable tag values remain shared. §10.1
  2. A property is a data descriptor, so its getter runs before the instance dictionary value. §10.2, §10.5
  3. Final, Left, Right, Base, object, assuming the stated consistent parent order. §10.4
  4. Check that bases do not supply an instance dictionary, and that every needed dynamic attribute is declared (or __dict__ is explicitly included). Also avoid assuming a fixed byte saving across implementations. §10.2

2 · Extensible service design · 20 minutes

A service can run with either of two transports and either of two output formats. Plugins register implementations with decorators. A team is considering a metaclass, a singleton, and singledispatch.

  1. Choose a construction pattern if transport and format combinations must be compatible. (3 marks)
  2. Describe how a decorator can register each plugin and what it should return. (3 marks)
  3. Explain which argument singledispatch uses and when it is insufficient. (2 marks)
  4. Suggest a simpler subclass-registration mechanism and two tests for plugin contracts. (4 marks)
Show worked answer
  1. An abstract factory can create a compatible family of transport and formatter products; a small factory function may suffice if selection is simpler. §11.2
  2. A decorator receives the plugin, stores it under a stable key, then returns it or an intentional wrapper so the name remains meaningful. §11.3
  3. It dispatches on the first argument only; it is insufficient when behaviour depends on a pair of argument types. §11.1
  4. Use __init_subclass__ or a class decorator if sufficient. Test each implementation’s promised methods and test factory selection plus failure for an unknown key. §10.5, §10.3, §11.2–11.3

Slips in the notes

These points were checked against the lecture and current official Python documentation.

  • Slide 3, copying. The slide says copying requires copy.deepcopy(), but a shallow copy is also a copy; it creates a new outer compound object while keeping references to its elements. Use a deep copy only when recursive independence is intended, and note that copying everything may be inappropriate. Python copy documentation. §10.1
  • Slide 8, attribute lookup. The shown instance-dictionary then class-dictionary sequence is a sketch: data descriptors on the class take precedence over the instance dictionary, and non-data descriptors follow it. Descriptor guide. §10.2, §10.5
  • Slide 34, dispatch cost. The fixed “hashing, collision resolution, MRO traversal” cost is too categorical for modern Python: specialisation and inline caches can optimise common call sites. Treat performance as runtime- and workload-dependent, then profile. Python 3.11 specialisation notes. §11.1
