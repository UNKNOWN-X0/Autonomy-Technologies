9.1 Defensive programming

In plain words: make assumptions visible and each program part small enough to test.

A function contract states acceptable inputs and promised output. Modularity makes parts testable in isolation. Remove syntax and static errors first, then compare chosen input/output pairs with the specification.

Worked example · absolute value contract

  1. Assume x is an integer.
  2. Return x if x ≥ 0 and −x otherwise.
  3. Expected cases: 4→4, −4→4, 0→0.

Try a test contract

Trap: A function running once does not prove it meets its contract.

Near miss: Testing only x=4 misses a faulty zero boundary; add x=0.

Recall · §9.1

  1. What does a contract state?
  2. Why modularize?
Answers
  1. Input assumptions and the promised result. §9.1
  2. To test and debug pieces independently. §9.1

9.2 Test levels

In plain words: test one unit, keep tests for old bugs, and check components together.

  • Unit: one function.
  • Regression: prevent a fixed bug from returning.
  • Integration: check the combined program.

For each input, record an expected result before execution. Integration-only testing makes failures harder to localize.

Compare test levels

Trap: A passing unit test does not prove the integrated report is correct.

Near miss: Two functions pass alone but use mismatched record shapes; integration exposes it.

Recall · §9.2

  1. What does a regression test protect?
  2. What does integration testing check?
Answers
  1. A previously fixed defect. §9.2
  2. Whether components work together. §9.2

9.3 Black-box testing

In plain words: choose cases from the specification without looking at implementation.

Partition inputs into natural classes and test boundaries: empty/singleton, small/large, and either side of a decision. A square-root function might promise x≥0, ε>0 and x−ε≤r²≤x+ε.

Worked example · square-root cases

  1. (0, 0.0001) checks zero.
  2. (25, 0.0001) checks a perfect square.
  3. (0.05, 0.0001) checks values below one.
  4. (2, 0.0001) checks an irrational root against tolerance.
  5. Very small and large values probe extremes.

Build partitions

Trap: Many typical values can still miss a boundary.

Near miss: Testing −2 and 2 covers branches in the faulty abs example but misses −1.

Recall · §9.3

  1. Why test boundaries?
  2. Why can another person design tests?
Answers
  1. Boundary defects can be missed by ordinary examples. §9.3
  2. They can follow the specification without implementer bias. §9.3

9.4 Glass-box testing

In plain words: inspect decisions in code and exercise their outcomes.

Coverage and correctnessexecuted paths ≠ correct behaviorPair path checks with boundary cases from the specification.

Path-complete testing attempts every path, but loops have many lengths and coverage does not prove correctness. For faulty code if x < -1: return -x, tests 2 and −2 cover both branches, yet −1 returns −1, contrary to the absolute-value contract.

Worked example · coverage blind spot

  1. 2 takes the false branch and returns 2.
  2. −2 takes the true branch and returns 2.
  3. −1 takes the false branch and wrongly returns −1.
  4. The boundary test finds what branch coverage missed.

Exercise branches and boundaries

Trap: Path coverage is evidence of execution, not proof of correctness.

Near miss: A branch test with −2 nearly checks abs, but −1 reveals the wrong condition.

Recall · §9.4

  1. What does path-complete mean?
  2. What does coverage not guarantee?
Answers
  1. Every potential path was tested at least once. §9.4
  2. That every boundary or specification case is correct. §9.4

9.5 Debug systematically

In plain words: find how the unexpected value arose; do not guess at a fix.

Debugging loopobserve → hypothesis → repeatable testChange one cause at a time.

Observe evidence, form a hypothesis, and repeat a small experiment. Use a simple failing input. Print function entry, parameters and results. With bisection, inspect midway through a long calculation, then focus on the half containing the first divergence.

Worked example · find a wrong total

  1. Save the smallest failing input.
  2. Inspect an intermediate value halfway through.
  3. If wrong, inspect the earlier half; otherwise inspect the later half.
  4. Repeat to locate the first faulty operation.
  5. Change one thing and rerun this case and regression tests.

Try bisection debugging

Trap: Changing several lines before rerunning the case destroys useful evidence.

Near miss: A print at the final result shows failure but not where it began; inspect intermediate values.

Recall · §9.5

  1. Why ask how the result arose?
  2. What makes a debugging experiment useful?
Answers
  1. It focuses on the sequence of events and values. §9.5
  2. It is small, repeatable, and tests one hypothesis. §9.5

9.6 Exceptions and handlers

In plain words: Python raises an exception when an operation cannot proceed.

Handler matchraised type ∈ handled typesOtherwise the exception propagates.
  • IndexError: index outside a sequence.
  • NameError: a name is not defined.
  • TypeError: an operation received an inappropriate type.
  • ValueError: a suitable type carries an invalid value.
  • AttributeError: an attribute lookup failed.

A try body runs until an exception; a matching specific except handles it. Unmatched exceptions propagate.

Worked example · safe conversion

try: int(text) may raise ValueError; except ValueError can report a correction, and else runs only after success. Keep try narrow so unrelated errors remain visible.

Match errors and handlers

Trap: A bare except can hide a TypeError while handling a conversion error.

Near miss: Catching ValueError around the whole report almost works, but can mislabel a later ValueError; keep try narrow.

Recall · §9.6

  1. How do TypeError and ValueError differ?
  2. Why avoid bare except?
Answers
  1. Wrong operand type versus invalid value. §9.6
  2. It can hide unrelated programming errors. §9.6

9.7 Raise or recover deliberately

In plain words: catch an error only when there is a sensible next action.

Error policyrecover only when the next action is definedOtherwise raise or re-raise a descriptive exception.

Raise a descriptive exception if a function cannot meet its contract. Avoid magic error values that resemble valid results. A handler may notify, stop, apply a documented default, or re-raise. For empty grades, choose whether to reject or define a default average. Finally runs after success or failure, making it suitable for cleanup.

Worked example · empty grades

  1. sum(grades)/len(grades) raises ZeroDivisionError for an empty list.
  2. One policy rejects the list; another defines an average of 0.0.
  3. Document the choice so callers do not treat a default as measured data.

Choose an error policy

Trap: Returning a special number for failure can make it look like a valid result.

Near miss: Returning 0.0 for no grades is only valid if that policy is explicit.

Recall · §9.7

  1. When re-raise?
  2. What is finally for?
Answers
  1. When the function cannot safely recover. §9.7
  2. Cleanup regardless of success or failure. §9.7

9.8 Assertions and invariants

In plain words: assert says an internal condition should always hold here.

Assertionassert conditionChecks an internal assumption during development.

assert len(grades) > 0 raises AssertionError when false in a normal run. Assertions can check invariants and expected internal results during development. They supplement testing.

Python may omit assertions under optimization (-O). Do not use them for required behavior or user-input validation; validate external data explicitly.

Worked example · internal versus external

  1. Assert an internal count remains non-negative after an algorithm step.
  2. Explicitly reject invalid user input and display an error.
  3. The first checks a programmer assumption; the second is required behavior.

Check an invariant

Trap: An assertion is not a substitute for checking user data.

Near miss: assert age >= 18 looks like validation, but -O can remove it; use an explicit check.

Recall · §9.8

  1. What is an invariant?
  2. Why not assert external input?
Answers
  1. A condition expected to remain true. §9.8
  2. Optimization can remove assertions. §9.8

Exam-style problems

Allow about 20 minutes for each problem.

Problem 1 · Test a square-root function

Given x≥0, eps>0, and the promise x−eps≤r²≤x+eps, design a test set, explain coverage limits, and describe debugging a failure.

  1. Partition the inputs.
  2. State a boundary and extreme-value check.
  3. Explain the path-coverage limitation.
  4. Describe a debugging strategy.
Show worked answer
  1. Test zero, perfect squares, sub-unit values, irrational roots, and very small and large values. §9.3
  2. Check zero and extremes; evaluate the promised inequality instead of requiring one exact approximation. §9.3
  3. Exercise branches and loop exits, but keep boundary tests because execution coverage does not prove correctness. §9.4
  4. Keep the failing input and bisect intermediate values to find the first divergence. §9.5
